建议将这个项目定位为一套 基于 Go 的分布式网关远程运维管理平台（Gateway RMM）。

它不只是一个远程终端工具，而是一个由网关 Agent 和中心管理平台组成的统一运维系统。核心目标是：只要网关能够访问互联网，就可以通过服务器对网关进行实时监控、远程终端操作、文件管理、配置管理和软件升级。

我建议采用以下设计原则：

1. Agent + Server 架构：网关主动连接服务器，不要求网关拥有公网 IP，也不要求开放入站端口。
2. Go 全栈后端：宿主端和服务器端均使用 Go，便于共享通信协议、数据结构和业务模块。
3. 长连接 + 多路复用：控制通道保持长连接，终端、文件传输等使用独立会话通道。
4. 模块化设计：远程终端、文件管理、配置管理、监控、升级均作为独立功能模块。
5. 安全优先：设备身份认证、权限控制、操作审计、传输加密和命令执行限制必须纳入基础设计。

# 1. 项目概述

## 1.1 项目背景

随着物联网网关、工业控制器、边缘计算设备的部署数量不断增加，需要一套统一的远程运维管理平台，对分布在不同网络环境下的网关进行集中管理。

传统 SSH 远程管理方式存在以下问题：

1. 网关通常处于内网环境，没有公网 IP。
2. 需要配置端口映射、VPN 或专用网络。
3. 无法统一查看所有网关的运行状态。
4. 无法方便地通过浏览器进行远程文件管理。
5. 无法统一管理网关系统配置。
6. 无法对远程操作进行权限控制和审计。
7. 网关数量增加后，人工维护成本较高。

因此，需要开发一套基于 Go 语言的远程运维管理系统。

## 1.2 产品目标

构建一个中心化的网关管理平台，实现：

- 网关自动注册和身份认证。
- 网关主动连接管理服务器。
- 网关运行状态持续上报。
- 网关在线状态实时监控。
- 浏览器远程命令终端。
- 浏览器远程文件管理。
- 远程系统配置管理。
- 远程命令执行。
- 软件远程升级。
- 网关分组、标签和批量管理。
- 用户权限管理和操作审计。

## 1.3 系统组成

整个系统分为三个部分：

| 模块                | 运行位置 | 主要职责                |
| ----------------- | ---- | ------------------- |
| Gateway Agent     | 网关设备 | 运行状态采集、通信、远程任务执行    |
| Management Server | 云服务器 | 设备管理、连接管理、任务调度、数据存储 |
| Web Console       | 浏览器  | 设备管理、终端、文件、配置管理     |

其中 Web Console 可以与 Management Server 部署在同一个服务中。

## 2.1 系统架构

                      |
                HTTPS / WSS

          +-----------------------+
          |   Management Server  |
          |                       |
          |  Web API              |

          |  File Manager         |
          |  Config Manager       |

          +-----------+-----------+
                      |
               WebSocket / TLS
                      |
          +-----------+-----------+
          |                       |
     Gateway Agent A         Gateway Agent B
          |                       |
     +----+------+           +----+------+
     |           |           |           |
   System      Files       System      Files
   Process     Config      Process     Config
   Monitor     Terminal    Monitor     Terminal
```

## 2.2 核心设计原则

### 2.2.1 网关主动连接

所有网关主动向管理服务器发起连接。

不要求：

- 网关拥有公网 IP。
- 网关开放 SSH 端口。
- 路由器配置端口映射。
- 使用第三方 VPN。

只需要网关可以访问管理服务器的 HTTPS/WSS 端口。

### 2.2.2 长连接管理

每个网关启动 Agent 后，自动连接服务器。

连接建立后：

1. 完成设备身份认证。
2. 上报设备基础信息。
3. 上报当前运行状态。
4. 定期发送心跳。
5. 接收服务器下发的任务。
6. 执行远程管理操作。
7. 返回任务执行结果。

当网络中断时，Agent 自动重连。

### 2.2.3 控制通道和数据通道分离

建议采用两类通信通道：

- Control Channel：设备注册、心跳、状态上报、任务调度。
- Data Channel：远程终端、文件传输、配置文件传输等。

这样可以避免大文件传输阻塞心跳和控制指令。

## 3.3 设备身份管理

每个网关必须具有唯一设备 ID。

建议设备信息：

| 字段               | 说明       |
| ---------------- | -------- |
| device_id        | 唯一设备编号   |
| device_name      | 设备名称     |
| device_key       | 设备认证密钥   |
| hardware_id      | 硬件标识     |
| product_id       | 产品型号     |
| firmware_version | 固件版本     |
| agent_version    | Agent 版本 |
| os_type          | 操作系统     |
| architecture     | CPU 架构   |
| created_at       | 注册时间     |

设备首次启动时：

1. 读取本地设备身份。
2. 如果没有身份，则进入注册流程。
3. 向服务器发起注册请求。
4. 完成设备认证。
5. 获取设备凭证。
6. 保存本地身份信息。
7. 建立 WebSocket 长连接。

设备密钥需要安全保存，不能直接使用设备 ID 作为认证凭证。

## 3.4 自动连接与重连

Agent 必须实现稳定的连接管理机制。

功能要求：

- 启动自动连接服务器。
- 心跳检测。
- 网络断开自动重连。
- 支持指数退避。
- 加入随机抖动，避免大量设备同时重连。
- 网络恢复后自动上线。
- 连接超时检测。
- 服务端主动断开后的重连。
- 支持服务器地址动态配置。
- 支持连接状态监控。

建议心跳间隔：

- 默认 30 秒。
- 心跳超时阈值 90 秒。
- 重连间隔从 1 秒开始。
- 最大重连间隔 60 秒。

上述参数需要支持配置。

- 关闭网关。
- 重启指定服务。
- 查看系统日志。
- 修改系统时间。
- 网络诊断。
- 执行自定义脚本。

任务需要具备：

- 任务 ID。
- 任务类型。
- 执行参数。
- 创建时间。
- 执行状态。
- 执行结果。
- 超时时间。
- 错误信息。

任务状态：

```
PENDING
   |
   v
RUNNING
   |
   +------> SUCCESS
   |
   +------> FAILED
   |
   +------> TIMEOUT
   |
   +------> CANCELLED
```

对于具有破坏性的操作，例如删除文件、重启系统和执行高权限脚本，应提供独立权限控制和操作确认机制。

## 3.10 Agent 软件升级

支持服务器远程升级 Agent。

升级流程：

1. 服务器发布升级版本。
2. Agent 接收升级任务。
3. Agent 下载升级包。
4. 校验文件 SHA256。
5. 验证数字签名。
6. 备份当前程序。
7. 替换 Agent。
8. 重启 Agent。
9. 上报升级结果。
10. 启动失败时回滚。

升级包应区分操作系统和 CPU 架构。

# 5. 通信协议设计

## 5.1 通信方式

建议：

| 场景   | 协议                |
| ---- | ----------------- |
| 设备注册 | HTTPS             |
| 设备控制 | WebSocket + TLS   |
| 心跳   | WebSocket         |
| 状态上报 | WebSocket         |
| 任务下发 | WebSocket         |
| 终端数据 | 独立 WebSocket 会话   |
| 文件传输 | WebSocket 二进制分块   |
| 配置传输 | WebSocket / HTTPS |

## 5.2 消息结构

建议统一消息协议。

```
{
  "version": 1,
  "type": "heartbeat",
  "id": "message-id",
  "device_id": "gateway-001",
  "timestamp": 1793970000,
  "data": {}
}
```

消息类型建议：

| 类型            | 方向             | 说明     |
| ------------- | -------------- | ------ |
| register      | Agent → Server | 设备注册   |
| register_ack  | Server → Agent | 注册响应   |
| heartbeat     | Agent → Server | 心跳     |
| status_report | Agent → Server | 状态上报   |
| task_create   | Server → Agent | 任务下发   |
| task_result   | Agent → Server | 任务结果   |
| session_open  | Server → Agent | 打开远程会话 |
| session_close | Server → Agent | 关闭远程会话 |
| config_sync   | Server → Agent | 配置同步   |
| upgrade       | Server → Agent | 软件升级   |
| error         | 双向             | 错误消息   |

建议消息协议与传输层分离，后续可以支持 JSON、MessagePack 或 Protobuf。

## 5.3 数据通道设计

不建议所有功能都通过同一个 WebSocket 连接传输。

建议：

```
Agent
  |
  +---- Control WebSocket
  |       |
  |       +-- Heartbeat
  |       +-- Status
  |       +-- Task
  |       +-- Config
  |
  +---- Terminal WebSocket
  |
  +---- File Transfer WebSocket
  |
  +---- Upgrade Channel
```

控制通道保持轻量，避免文件传输和终端输出影响心跳。

每个数据会话由服务端创建唯一 Session ID，并绑定设备 ID、用户 ID、权限和有效期。

# 8. 安全设计

安全是整个系统的基础要求。

## 8.1 设备认证

- 每台设备使用独立身份凭证。
- 禁止所有设备共用固定密钥。
- 首次注册需要授权。
- 支持设备凭证吊销。
- 支持设备密钥轮换。
- 支持 TLS 双向认证或安全的设备令牌认证机制。

## 8.2 传输安全

- 所有外部通信使用 TLS。
- WebSocket 使用 WSS。
- 文件传输进行完整性校验。
- 防止消息重放。
- 重要操作进行二次授权。

## 8.3 远程终端安全

- 默认不向普通用户开放 root 权限。
- 支持按角色限制终端访问。
- 支持终端会话超时。
- 支持终端会话主动终止。
- 记录终端操作审计。
- 支持高风险命令审批策略。

## 8.4 文件安全

- 限制文件访问范围。
- 禁止路径穿越。
- 校验符号链接。
- 限制文件大小。
- 限制并发传输数量。
- 记录文件上传、下载和删除操作。

## 8.5 远程升级安全

- 升级包数字签名。
- SHA256 校验。
- 版本校验。
- 升级失败自动回滚。
- 防止降级攻击。
- 升级任务操作审计。

# 15. 最终架构建议

建议最终采用以下技术路线：

**Agent：**

- Go 开发。
- 单文件二进制。
- Linux ARM/ARM64/x86_64。
- WebSocket 长连接。
- 模块化功能设计。
- 独立终端、文件、配置、监控模块。

**Server：**

- Go 开发。
- 模块化单体架构。
- HTTP API + WebSocket。
- PostgreSQL。
- Redis 按需引入。
- 统一设备连接管理。
- 独立会话中继模块。

**Web：**

- Vue 3。
- Element Plus。
- xterm.js。
- WebSocket。
- 文件管理器。
- 设备监控仪表盘。

**通信：**

- HTTPS 注册。
- WSS 长连接。
- 控制通道与数据通道分离。
- 统一消息协议。
- 支持会话 ID 和请求 ID。

**核心开发原则：**

先实现一个稳定、轻量、可靠的 Go Agent，再实现服务器连接管理和 Web 远程运维功能。不要一开始就拆分成大量微服务，也不要过早引入复杂的消息队列。

第一版重点做好四件事：设备连接、状态监控、远程终端、远程文件管理。之后再逐步增加配置管理、升级管理和批量运维。

## 我的额外设计建议

有三个架构问题建议在正式编码前确定：

1\. 不要把 Agent 设计成单纯的远程 Shell 客户端。

建议把 Agent 做成通用网关运行时管理程序，未来可以通过插件扩展 MQTT 状态、Modbus 设备状态、IoT 应用运行状态等信息。这样它不仅能管理 Linux 系统，还能管理网关上运行的物联网业务。

2\. 远程终端和远程任务必须分开。

- 终端：长期交互式会话，采用 PTY。
- 任务：一次性命令执行，有超时、结果、状态和审计。
- 文件：独立的数据传输会话。

三者不要混用同一个执行接口。

3\. 第一版就设计好设备身份和权限体系。

后续网关数量增加、多租户管理、设备分享、代理商管理时，不需要推翻原来的认证架构。

我建议下一步直接进入 V1.0 系统详细架构设计，重点把 Agent、Server、通信协议、会话管理、目录结构和核心 Go 接口设计完整，然后再开始编码。


这次建议把设计提升到平台级，而不是简单增加几个 Agent 功能。

我建议将系统定义为：

Gateway RMM：分布式网关远程管理与运维平台

重点增强两部分：

- Agent： 从简单的状态上报程序，升级为具备设备管理、系统管理、任务执行、终端代理、文件服务、配置同步、插件扩展能力的网关管理运行时。
- Server： 从简单的 WebSocket 服务，升级为具备设备连接管理、会话路由、任务调度、数据中继、权限控制、状态管理和集群扩展能力的中心控制平台。
- 通信协议： 不只是定义几个 JSON 消息，而是设计一套具备请求响应、异步事件、流式传输、消息确认、超时、重试、断点续传和版本兼容能力的完整协议。

# 第一部分：总体架构

## 1.1 系统定位

Gateway RMM 是一套面向物联网网关、工业网关、边缘计算设备的远程管理平台。

通过部署轻量级 Agent，使网关主动连接中心服务器，实现设备管理、系统监控、远程终端、文件管理、配置管理、应用管理、远程升级等能力。

系统需要具备：

1. 大规模设备接入能力。
2. 稳定的长连接管理能力。
3. 双向远程控制能力。
4. 多路数据传输能力。
5. 可靠的任务执行能力。
6. 灵活的功能扩展能力。
7. 完善的设备认证与权限管理能力。
8. 多 Server 节点水平扩展能力。

## 1.3 设计原则

### Agent 原则

- 核心程序尽量轻量。
- 功能模块独立。
- 功能通过统一接口注册。
- 统一任务执行框架。
- 统一事件系统。
- 统一通信接口。
- 不允许业务模块直接操作底层连接。
- 支持功能按需启用。

### Server 原则

- 连接管理和业务管理分离。
- 消息路由和任务调度分离。
- 设备状态和连接状态分离。
- 实时会话和持久任务分离。
- 允许多个 Server 实例同时运行。
- 设备连接可以被不同业务模块使用。

### Protocol 原则

- 统一消息头。
- 统一消息类型。
- 统一请求响应机制。
- 统一错误码。
- 支持事件推送。
- 支持多路会话。
- 支持流式传输。
- 支持协议版本协商。
- 支持断线恢复。
- 支持消息幂等。

## 2.4 统一组件接口

Agent 内所有功能模块实现统一接口。

```
type Component interface {
    Name() string

    Init(ctx context.Context, agent AgentContext) error

    Start(ctx context.Context) error

    Stop(ctx context.Context) error

    Status() ComponentStatus
}
```

功能模块通过注册机制加载。

```
type Registry interface {
    Register(component Component) error

    Get(name string) (Component, bool)

    List() []Component

    StartAll(ctx context.Context) error

    StopAll(ctx context.Context) error
}
```

每个组件可以注册自己的通信命令。

```
type Handler interface {
    Handle(
        ctx context.Context,
        request *Request,
    ) (*Response, error)
}
```

建议组件通过 Agent 提供的接口访问系统能力，避免各模块直接依赖 WebSocket、数据库等基础设施。

# 第四部分：GRP 通信协议设计

# 4. 协议概述

## 4.1 协议名称

GRP：Gateway Remote Protocol。

用于 Agent 和 Server 之间的双向通信。

GRP 不是单纯的 RPC 协议，而是一套支持控制、事件、任务和流式数据传输的应用层协议。

## 4.2 协议分层

```
+-----------------------------------+
|          Application Layer        |
|                                   |
| Device / System / Terminal        |
| File / Config / Task / Upgrade    |
+-----------------------------------+
|           GRP Protocol            |
|                                   |
| Envelope / Request / Response     |
| Event / Stream / Error            |
+-----------------------------------+
|           Codec Layer             |
|                                   |
| Protobuf / Binary / JSON          |
+-----------------------------------+
|          Transport Layer          |
|                                   |
| WebSocket / TLS                   |
+-----------------------------------+
|           TCP / IP                |
+-----------------------------------+
```

## 4.3 传输层选择

第一版推荐：

- TCP。
- TLS 1.3。
- WebSocket。
- Protobuf。

Agent 主动建立一个长期 WSS 连接。

在该连接上实现逻辑多路复用。

不建议初期为心跳、终端、文件、配置分别建立独立 TCP 连接，因为这会增加连接数量、认证成本和网络资源消耗。

但是必须通过逻辑 Stream 隔离不同业务的数据流。

## 4.4 通信方向

GRP 支持双向通信：

| 类型       | 方向 | 说明    |
| -------- | -- | ----- |
| Request  | 双向 | 请求    |
| Response | 双向 | 响应    |
| Event    | 双向 | 事件    |
| Stream   | 双向 | 连续数据流 |
| Control  | 双向 | 控制消息  |

Server 可以主动向 Agent 发送请求，Agent 也可以主动向 Server 发送请求。

## 4.5 消息编码

推荐使用 Protobuf。

原因：

- 消息结构明确。
- 数据体积小。
- Go 支持成熟。
- 字段兼容性好。
- 便于多语言扩展。

协议开发阶段可以提供 JSON 调试编码，但生产默认使用 Protobuf。

# 5. GRP 消息结构

## 5.1 统一消息头

所有 GRP 消息采用统一 Envelope。

```
syntax = "proto3";

package grp.v1;

option go_package = "gateway/pkg/protocol/grpv1";

enum MessageKind {
    MESSAGE_KIND_UNSPECIFIED = 0;
    REQUEST = 1;
    RESPONSE = 2;
    EVENT = 3;
    STREAM = 4;
    CONTROL = 5;
}

message Envelope {
    uint32 version = 1;

    MessageKind kind = 2;

    string type = 3;

    string message_id = 4;

    string request_id = 5;

    string session_id = 6;

    string device_id = 7;

    uint64 sequence = 8;

    int64 timestamp = 9;

    uint32 flags = 10;

    bytes payload = 11;

    string trace_id = 12;
}
```

字段说明：

| 字段         | 说明            |
| ---------- | ------------- |
| version    | 协议版本          |
| kind       | 消息类型          |
| type       | 具体业务消息名称      |
| message_id | 消息唯一 ID       |
| request_id | 请求关联 ID       |
| session_id | 会话 ID         |
| device_id  | 设备 ID         |
| sequence   | 消息序号          |
| timestamp  | Unix 毫秒时间戳    |
| flags      | 消息标志          |
| payload    | Protobuf 业务数据 |
| trace_id   | 链路追踪 ID       |

说明：

- message_id 每条消息唯一。
- request_id 用于请求响应关联。
- session_id 用于会话关联。
- sequence 用于流内数据顺序和检测缺失。
- trace_id 用于跨模块追踪。
- payload 根据 type 解码为具体消息结构。

建议所有消息统一使用 Envelope，但不同业务消息需要定义独立 Protobuf 类型。

## 5.2 消息类型命名

采用：

```

```

例如：

```

# 7. 心跳与状态上报协议

## 7.1 心跳

    int64 server_time = 1;
    uint32 next_heartbeat_interval = 2;

# 9. Stream 多路复用协议

这是整个系统最重要的通信设计之一。

## 9.1 设计目的

终端、文件、日志、诊断等功能都属于连续数据流。

如果每个功能单独创建 WebSocket，将增加连接管理成本。

因此建议实现逻辑多路复用。

一个 Agent WSS 连接可以同时承载：

```
WSS Connection
     |
     +--- Stream 1: Control
     |
     +--- Stream 2: Terminal A
     |
     +--- Stream 3: Terminal B
     |
     +--- Stream 4: File Upload
     |
     +--- Stream 5: File Download
     |
     +--- Stream 6: Log Stream
     |
     +--- Stream 7: Diagnostic
```

## 9.2 Stream 消息

```
enum StreamAction {
    STREAM_UNSPECIFIED = 0;
    OPEN = 1;
    OPEN_ACK = 2;
    DATA = 3;
    WINDOW_UPDATE = 4;
    HALF_CLOSE = 5;
    CLOSE = 6;
    RESET = 7;
}

message StreamFrame {
    uint32 stream_id = 1;
    StreamAction action = 2;
    uint64 offset = 3;
    bytes data = 4;
    uint32 window_size = 5;
    string content_type = 6;
}
```

## 9.3 Stream 生命周期

```
OPEN
  |
  v
OPEN_ACK
  |
  v
ACTIVE
  |
  +---- DATA
  |
  +---- WINDOW_UPDATE
  |
  +---- HALF_CLOSE
  |
  v
CLOSE
```

异常时：

```
ACTIVE
  |
  v
RESET
```

## 9.4 Stream 规则

- stream_id 在连接范围内唯一。
- 0 保留给控制通道。
- 不同 Stream 相互独立。
- 每个 Stream 独立维护序号。
- 每个 Stream 独立维护流量窗口。
- 支持半关闭。
- 支持主动关闭。
- 支持异常重置。
- 连接关闭时清理所有 Stream。

## 9.5 流量控制

必须实现背压机制。

例如文件传输速度过快，接收方来不及写入磁盘，就通过 WINDOW_UPDATE 控制发送方继续发送的数据量。

建议：

- 单个 Stream 独立流量窗口。
- 全连接设置总发送缓冲区上限。
- 发送队列达到阈值时暂停读取上游数据。
- 恢复窗口后继续传输。
- 慢消费者不能无限占用内存。

注意：WebSocket 本身不提供 HTTP/2 那样的多路流量控制能力，GRP 必须在应用层实现这些机制。

# 第五部分：连接可靠性与集群设计

# 16. 连接可靠性

## 16.1 断线重连

采用指数退避：

```
1s -> 2s -> 4s -> 8s -> 16s -> 32s -> 60s
```

增加随机抖动，避免大量设备同时重连。

## 16.2 断线恢复

重连后 Agent 应执行：

1. 重新认证。
2. 重新注册连接。
3. 上报设备信息。
4. 上报组件状态。
5. 上报未完成任务状态。
6. 同步配置版本。
7. 同步 Agent 能力。
8. 清理已失效会话。
9. 重新接收任务。

## 16.3 消息可靠性

不能要求所有消息都可靠投递。

建议区分：

| 消息类别 | 可靠性    |
| ---- | ------ |
| 心跳   | 尽力而为   |
| 实时状态 | 最新值优先  |
| 设备事件 | 有限持久化  |
| 配置下发 | 必须确认   |
| 远程任务 | 持久化确认  |
| 文件传输 | 偏移量与校验 |
| 终端数据 | 有序实时传输 |
| 升级任务 | 持久化确认  |

重要任务应采用至少一次投递 + 幂等执行设计，而不是假设网络可以提供端到端恰好一次执行。

# 17. Server 集群设计

## 17.1 多节点架构

```
                Load Balancer
                      |
          +-----------+-----------+
          |           |           |
       Server A    Server B    Server C
          |           |           |
          +-----------+-----------+
                      |
                 Redis / NATS
                      |
                 PostgreSQL
                      |
                 Object Storage
```

## 17.2 连接归属

每台设备同时只能存在一个有效的主连接。

连接注册时记录：

```
device_id
connection_id
server_node_id
connected_at
last_seen_at
```

设备重新连接时，Server 必须处理旧连接替换，避免出现双连接竞争。

## 17.3 跨节点消息路由

例如：

- 网关 A 连接 Server A。
- 用户请求由 Server B 接收。
- Server B 查询设备连接归属。
- Server B 通过消息总线将请求发送到 Server A。
- Server A 将请求写入网关 A 的连接。
- 响应按照原路返回。

Redis 可以用于连接归属缓存，NATS 或 Redis Streams 可以承担跨节点消息传递。

不要把 Redis Pub/Sub 当成可靠任务队列，关键任务必须持久化。

## 17.4 节点故障

Server 节点故障时：

- Agent 自动重新连接。
- 负载均衡器将新连接分配给健康节点。
- Agent 重新认证。
- 设备重新注册连接归属。
- 任务管理器检查未完成任务。
- 会话管理器清理失效会话。
- 终端会话重新建立。

不建议第一版实现透明迁移终端 PTY 状态。连接断开后终端会话可以重建，但原有 Shell 进程是否保留需要单独设计。

# 第六部分：安全体系

# 18. 设备身份安全

每台设备必须具备独立身份。

建议：

- 首次注册使用预置注册凭证或人工授权。
- 服务器为设备签发独立证书。
- 后续使用 mTLS 或证书绑定的设备身份认证。
- 私钥优先保存在安全硬件或受限文件中。
- 支持证书吊销。
- 支持证书轮换。
- 支持设备禁用。
- 支持重新注册审批。

设备认证和用户权限是两个不同层次。

设备通过认证，不代表用户自动拥有远程管理权限。

# 19. 消息安全

- 全程 TLS。
- 校验消息长度。
- 校验消息版本。
- 校验消息来源。
- 请求设置有效期。
- 高风险操作增加防重放保护。
- 文件数据进行完整性校验。
- 关键操作进行审计。

        messageType string,

# 第十部分：最终技术决策

| 项目        | 最终建议             |
| --------- | ---------------- |
| Agent 语言  | Go               |
| Server 语言 | Go               |
| Web 前端    | Vue 3            |
| 终端组件      | xterm.js         |
| 终端实现      | Linux PTY        |
| 通信协议      | GRP              |
| 数据编码      | Protobuf         |
| 传输协议      | WebSocket + TLS  |
| 多路复用      | 应用层 Stream       |
| 数据库       | PostgreSQL       |
| 缓存        | Redis            |
| 消息总线      | NATS（集群阶段）       |
| 文件存储      | 本地 / S3 兼容对象存储   |
| 设备认证      | mTLS / 设备证书      |
| 部署        | Systemd / Docker |

最终架构采用：

**一个 Agent + 一个长连接 + 多个逻辑 Stream + 多个功能组件 + 一个统一 Server 控制平台。**

这是整个项目最重要的架构基础。

协议、组件、任务和会话均独立设计，使系统后续能够增加更多网关管理能力，而不需要修改底层通信架构。
